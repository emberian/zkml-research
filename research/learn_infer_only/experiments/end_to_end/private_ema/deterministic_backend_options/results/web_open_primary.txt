L336: 1.0.0 (const: 1.94.0) · cite214†Source L337: #### pub const fn cite78†mul_add (self, a: cite201†f64 , b: cite201†f64 ) -> cite201†f64 L338: 
L339: Fused multiply-add. Computes `(self * a) + b` with only one rounding error, yielding a more accurate result than an unfused multiply-add.
L340: 
L341: Using `mul_add` may be more performant than an unfused multiply-add if the target architecture has a dedicated `fma` CPU instruction. However, this is not always true, and will be heavily dependant on designing algorithms with specific target hardware in mind.
L342: ##### cite215†§ Precision
L343: 
L344: The result of this operation is guaranteed to be the rounded infinite-precision result. It is specified by IEEE 754 as `fusedMultiplyAdd` and guaranteed not to change.
L345: ##### cite216†§ Examples
L346: 
L347:     `let m = 10.0_f64;
L348:     let x = 4.0_f64;
L349:     let b = 60.0_f64;
L350: 
L351:     assert_eq!(m.mul_add(x, b), 100.0);
L352:     assert_eq!(m * x + b, 100.0);
L353: 
L354:     let one_plus_eps = 1.0_f64 + f64::EPSILON;
L355:     let one_minus_eps = 1.0_f64 - f64::EPSILON;
L356:     let minus_one = -1.0_f64;
L357: 
L358:     // The exact result (1 + eps) * (1 - eps) = 1 - eps * eps.
L359:     assert_eq!(one_plus_eps.mul_add(one_minus_eps, minus_one), -f64::EPSILON * f64::EPSILON);
L360:     // Different rounding with the non-fused multiply and add.
L361:     assert_eq!(one_plus_eps * one_minus_eps + minus_one, 0.0);`
L362: 1.38.0 · cite217†Source L363: #### pub fn cite50†div_euclid (self, rhs: cite201†f64 ) -> cite201†f64 L364: 
L365: Calculates Euclidean division, the matching method for `rem_euclid`.
L366: 
L367: This computes the integer `n` such that `self = n * rhs + self.rem_euclid(rhs)`. In other words, the result is `self / rhs` rounded to the integer `n` such that `self >= n * rhs`.
L368: 
L369: ##### cite218†§ Precision
L370: 
L371: The result of this operation is guaranteed to be the rounded infinite-precision result.
L372: ##### cite219†§ Examples
L373: 
L374:     `let a: f64 = 7.0;
L375:     let b = 4.0;
L376:     assert_eq!(a.div_euclid(b), 1.0); // 7.0 > 4.0 * 1.0
L377:     assert_eq!((-a).div_euclid(b), -2.0); // -7.0 >= 4.0 * -2.0
L378:     assert_eq!(a.div_euclid(-b), -1.0); // 7.0 >= -4.0 * -1.0
L379:     assert_eq!((-a).div_euclid(-b), 2.0); // -7.0 >= -4.0 * 2.0`

L381: 1.38.0 · cite220†Source L382: #### pub fn cite84†rem_euclid (self, rhs: cite201†f64 ) -> cite201†f64 L383: 
L384: Calculates the least nonnegative remainder of `self` when divided by `rhs`.
L385: In particular, the return value `r` satisfies `0.0 <= r < rhs.abs()` in most cases. However, due to a floating point round-off error it can result in `r == rhs.abs()`, violating the mathematical definition, if `self` is much smaller than `rhs.abs()` in magnitude and `self < 0.0`. This result is not an element of the function’s codomain, but it is the closest floating point number in the real numbers and thus fulfills the property `self == self.div_euclid(rhs) * rhs + self.rem_euclid(rhs)` approximately.
L386: ##### cite221†§ Precision
L387: 
L388: The result of this operation is guaranteed to be the rounded infinite-precision result.
L389: 
L390: ##### cite222†§ Examples
L391: 
L392:     `let a: f64 = 7.0;
L393:     let b = 4.0;
L394:     assert_eq!(a.rem_euclid(b), 3.0);
L395:     assert_eq!((-a).rem_euclid(b), 1.0);
L396:     assert_eq!(a.rem_euclid(-b), 3.0);
L397:     assert_eq!((-a).rem_euclid(-b), 1.0);
L398:     // limitation due to round-off error
