## Exact arithmetic versus NTT modulus conversion

[SOURCE] The generic Karatsuba blind rotation uses the existing signed decomposition, monomial permutations, and `polynomial_wrapping_mul`/`polynomial_wrapping_add_mul_assign` (`karatsuba_pbs.rs:237–308,332–413`). The latter dispatch to wrapping Karatsuba for power-of-two N>64 (`T/src/core_crypto/algorithms/polynomial_algorithms.rs:331`), with integer wrapping multiply-add leaves (`1164–1205`). `lwe_ciphertext_modulus_switch` is generic over input/output scalar (`T/src/core_crypto/algorithms/modulus_switch.rs:14`); its common rounding is `(x + 2^(w-r-1) mod 2^w) >> (w-r)` for r<w (`T/src/core_crypto/fft_impl/common.rs:10`). The decomposition's apparent “random” tie bit comes from the input's rounding bit, not an RNG (`T/src/core_crypto/commons/math/decomposition/decomposer.rs:156–184`). Imports from an `fft_impl` directory here supply integer decomposition utilities, not a Fourier transform.

[DERIVED] For dimensionally valid initialized inputs, native u32 modulus, specified integer rounding and terminating memory-safe execution, these operations define one output coefficient vector independent of reduction order in the ring. That is a mathematical reason to investigate portable recomputation; this note does not prove Rust execution, memory safety, compiler lowering, or the cryptographic plaintext theorem. Exact integer output also need not equal old FFT output bytes.

[SOURCE] Both NTT PBS variants use `tfhe_ntt::prime64::Plan`. `try_new` checks prime modulus, power-of-two polynomial size at least16, and a primitive 2N-th root (`N/src/prime64.rs:761–775`); the plan also chooses modular-reduction implementations according to the prime and available SIMD. `Ntt64::new` rejects native/power-of-two transform moduli (`T/src/core_crypto/commons/math/ntt/ntt64.rs:34–54`). The BNF example uses Goldilocks p=2^64−2^32+1, native u64 user modulus and `NttLweBootstrapKeyOption::Raw` (`ntt64_bnf_pbs.rs:31–44,86–103`). The example expressly disclaims guaranteed security/correctness. The saved tests include a BNF custom parameter case (`T/src/core_crypto/algorithms/test/lwe_programmable_bootstrapping.rs:1163`); they were read, not run.

[SOURCE] `convert_standard_lwe_bootstrap_key_to_ntt64` accepts only u64 standard/NTT BSK containers and requires equal geometry and decomposition parameters (`T/src/core_crypto/algorithms/lwe_bootstrap_key_conversion.rs:294–364`). It either transforms already-prime coefficients or modulus-switches MSB-aligned power-of-two coefficients. BNF uses a Raw BSK and normalizes on the inverse path (`ntt64_bnf_pbs.rs:669`). For a power-of-two width w, the source converts x to p with `(floor(x/2^(64-w))*p + 2^(w-1)) >> w`. Its inverse uses integer division with the numerator `((x << w) | (p >> 1))` and then MSB alignment; the bitwise OR is the actual source operation (`ntt64.rs:144–172`). These formulas are not a claim that conversion preserves old ciphertext coefficients.

[HYPOTHESIS] A u32→u64 MSB embedding into a custom 2^32 modulus could reduce the BNF adapter's key-setup differences, starting from retained standard u32 BSK coefficients. This needs a phase/encoding/decomposition compatibility proof, modulus-conversion error analysis, output conversion, and actual API checks. Fresh u64 parameters are another route but require a new reviewed setup. The current Boolean noise bound does not automatically certify either route.

[SOURCE] `N/README.md:7–16` states the native CRT product agrees with wrapping arithmetic while the full signed integer result stays below half the CRT-prime product in magnitude; the binary variant assumes one **multiplicand polynomial** has 0/1 coefficients. Secret keys being binary does not make general external-product decomposition polynomials binary. `Plan32` uses primes 1062862849,1063059457,1064697857 (`N/src/lib.rs:453–455`) and performs six forward plus three inverse prime transforms per high-level product (`N/src/native32.rs:410–430`).

[EXECUTED: integer bound only] Their product is 1202987632058935920173056001. At N=1024, even the conservative bound N(2^32−1)^2=18889465922682487833600 lies below half that product; six such products also fit. The script records both inequalities. This supports one precise native32 multiplication/accumulation seam, not an implemented PBS wrapper or a cross-SIMD proof. No transform was run.

## Cost evidence and the first useful stopping point

[SOURCE] The public Karatsuba PBS documentation directs users to the FFT implementation for efficiency (`karatsuba_pbs.rs:68–70`), and the polynomial implementation documents O(N^1.58) wrapping multiplication (`polynomial_algorithms.rs:1080`). The [upstream release notes](https://github.com/zama-ai/tfhe-rs/releases) describe the added Karatsuba blind rotation as useful for checking implementations. This is an integer reference path; no CPU latency number was found in the searched cached crate source or targeted primary search results.

[DERIVED; computed in source_audit.json] For the existing source parameter geometry, a standard u32 BSK has n*l*(k+1)^2*N = 15427584 coefficients, or **61710336 coefficient bytes**, excluding KSK, allocation overhead and serialization metadata. A PBS has at most n*l*(k+1)^2 = **15066 polynomial products**, since zero modulus-switched mask coefficients skip work. At N=1024 the existing Karatsuba recursion has 3^4=81 schoolbook leaves of64×64 products: at most **4998537216 u32 scalar multiply-accumulates per PBS**, excluding additions, decomposition and key switching. These are source loop counts, not processor instructions or measured time. They argue for a polynomial/external-product adapter check before any full 538-gate Learn experiment; no duration is extrapolated.

[OPEN] Native32 CRT acceleration could lower that reference cost, but the pinned TFHE `src/` search has no `native32` use. A polynomial primitive must be integrated into the existing external-product traversal, preserve decomposition/normalization and accumulation bounds, and retain standard key coefficients. Pretransforming keys changes storage and needs its own cost accounting. HPU Goldilocks transforms and their hardware bandwidth are a separate backend; the prior [HPU seam note](/Users/ember/dev/zkml-research/notes/hpu-seam-study.md) is not CPU Boolean latency evidence.

## The floating-point alternative has a precise unclosed contract

[SOURCE] Fixed Dif4 removes timed plan selection; it does not alone freeze all numerical paths. `F/src/unordered.rs:295–346` still has x86 SIMD versus scalar dispatch. The pinned twiddle generator is the local `sincospi64` FMA polynomial (`F/src/fft_simd.rs:237–295`), not simply a call to the unspecified-precision platform `sin`/`cos`. Rust documents a correctly rounded fused result for [`f64::mul_add`](https://doc.rust-lang.org/std/primitive.f64.html#method.mul_add). Consequently, “all floats are nondeterministic” is not the finding.

[HYPOTHESIS: sufficient numerical contract] A portable FFT successor could specify exact binary64 constants/twiddle bytes; an identical ordered add/multiply/FMA operation graph; round-to-nearest ties-to-even for those arithmetic steps; fixed torus conversion and decomposition rules; finite intermediates; specified signed-zero/subnormal behavior; no reassociation or implicit FMA changes; and architecture-independent serialization. It would need either one explicit scalar path or a proof that every selected SIMD path implements that same graph and bit result. Then public inputs determine the same output bytes, conditional on the compiler/runtime satisfying that contract. We have neither established these premises for fixed Dif4 nor proved the full numerical program.

[SOURCE] Zama's [deterministic parallelized PBS documentation](https://docs.zama.ai/tfhe-rs/0.5-3/how-to/parallelized_pbs) concerns operation ordering for multi-bit PBS. It does not state a cross-platform numerical/serialization contract for this classic Boolean FFT path. [EXECUTED: scoped absence] The saved `rg` searches find no `deterministic|reproducib|cross.platform|cross.arch` text in cached `F/README.md` and `F/src`, and no NTT/Karatsuba entry point in cached Boolean `src/` (the “deterministic” hits concern seeding/tests). This is a search result over that version/corpus, not a claim about all TFHE implementations.
