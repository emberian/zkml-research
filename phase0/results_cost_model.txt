THE LOAD-BEARING ASSUMPTION: is the renormalizing shift STATIC?
======================================================================================
  bf16 carries a PER-ELEMENT exponent, so converting a block-float
  accumulator to bf16 needs THIS element's leading one -- data-dependent.
  Price the dynamic version and see whether the verdict survives.

                                       cols   lk   commit    piop   SPEEDUP
  static shift (assumed above)            3    2    3.09x   3.00x     2.63x
  dynamic per-element normalization       4    4    1.70x   1.50x     1.54x

  dynamic-normalization sweep: 0.85x .. 1.99x, median 1.42x, 54 of 54 below 2x

  If normalization is dynamic, the honest range straddles 2x and the
  thesis is not safe. Resolving static-vs-dynamic is the highest-value
  next measurement, and it is a SPEC question (what does the block-float
  spec say the output format is), not a prover question.

======================================================================================
ABLATION -- where does the bf16 advantage actually come from?
======================================================================================
  Turn off one structural difference at a time, at the baseline point.
  baseline                                         2.63x
  ...if int-q had a saturation value (no clamping)  1.85x   (clamping is worth +0.77x)
  ...if the scale were a power of two (f = 0)       1.94x   (the multiplier is worth +0.69x)
  ...both                                           1.05x

  Whatever survives (c) is the pure accumulator-width effect: a
  block-float 26-bit window vs a 34-bit int-12 accumulator.

======================================================================================
THE OPTIMISTIC BOUND -- what the plan ASSUMES (renormalization is free)
======================================================================================
  If the bf16 path really paid NOTHING to get from a matmul accumulator
  back to a bf16 table index -- the plan's 'requantization is ABSENT' --
  then bf16 costs 1 committed column + 1 lookup per element and nothing
  else. Price that too, so the gap between the two readings is visible.
  committed elements : 826,736,640   vs quantized 5,615,616,000   ratio 6.79x
  PIOP fraction-rows : 165,347,328   vs quantized 991,002,624   ratio 5.99x
  BLENDED SPEEDUP (ideal, renorm free, requant elems vanish) : 4.51x

  The gap between this and the honest number is the price of the
  assumption that renormalization is free. It is not free: a block-float
  accumulator must be normalized and rounded to index a bf16 table, and
  that step has exactly the requantization shape.

WHEN WOULD THE RANK-1 exp SPLIT ACTUALLY BUY ANYTHING?
======================================================================================
  eprint 2026/1390 Prop 3 governs the PER-PROOF table term only, and
  Corollary 3 says the per-lookup term is Omega(m) regardless. So the
  rank-1 split can only matter when the table term is a real share of
  the proof. Find the break-even.

  one dense 2^16 table costs        : 327,680 committed elements
  one bf16 element costs            : 11 committed elements
  elements per proof for the table
    to be 50% of the proof          : 29,789
    to be 10% of the proof          : 268,101
    to be  1% of the proof          : 2,949,120
  actual elements in a GPT-2 seq-512 proof : 165,150,720
  -> table term is 0.0541% of the proof

  if the proof is split into     1 chunks ( 165,150,720 elems each): table term  0.054%
  if the proof is split into    12 chunks (  13,762,560 elems each): table term  0.645%
  if the proof is split into   144 chunks (   1,146,880 elems each): table term  7.229%
  if the proof is split into  1728 chunks (      95,573 elems each): table term 48.322%

  Reading: rank-1 would divide the table term by ~256. At the measured
  operating point that term is a fraction of a percent, so the certified
  rank-1 optimum is worth a fraction of a percent. It only becomes
  interesting for proofs of a few tens of thousands of elements.
