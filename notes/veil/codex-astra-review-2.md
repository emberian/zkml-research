# Codex (gpt-6-astra, read-only) review of the Ariadne device and pilot, 2026-11-06

**A1–A3 hold only with important qualifications; A4 overclaims; A5 does not establish a closed inductive proof as stated.** I successfully rechecked both core Lean files and evaluated the traces below. I did not rerun the full Veil SMT checks.

1. **A1 is too weak to stand for state continuity.** [AriadneStep.lean:400](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:400) proves membership, not ordered-prefix preservation, multiplicity, unique occurrence IDs, or uniqueness of resumed state. `Sub` likewise forgets order and multiplicity (line 165). Until something is forwarded, the conclusion is vacuous. The paper instead constrains successive module executions and their inputs ([paper:1154](/Users/ember/paperbin/strackx2016-ariadne-state-continuity.txt:1154)). No fork attack against the full protocol follows merely from this weakness—but the theorem would not exclude forks retaining all previously forwarded entries.

2. **Duplicate forwards are real, including duplicate occurrence IDs.** Execute `arrive [7]; tick; forward; crash; restore (1,[e1]); tick×4; forward`. I evaluated this: `e1`, occurrence `1`, leaves at counters `1` and `3`. Recovery explicitly sets `queue := log` ([AriadneStep.lean:103](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:103)). Thus the old `forwarded_ids_nodup` guarantee advertised at [CommitStep.lean:16](/Users/ember/dev/degg-research/experiments/chokepoint-step/CommitStep.lean:16) is lost. Veil’s “downstream drops duplicates” comment ([ChokepointAriadne.lean:188](/Users/ember/dev/veil-pilot/VeilPilot/ChokepointAriadne.lean:188)) supplies no receiver model or proof. Its Boolean frame sets also erase multiplicity.

3. **Resurrection exists, but the paper explicitly permits this case.** Execute `arrive [7]; crash; restore (0,[]); tick×2; crash; restore (1,[e1]); tick×4; forward`. I evaluated this too: the abandoned entry resurfaces without its original commit tick. Recovery subsequently persists it before forwarding. This is precisely the paper’s permitted “Skipping Unprocessed Input” scenario ([paper:655](/Users/ember/paperbin/strackx2016-ariadne-state-continuity.txt:655)). Calling it a violation requires an externally observable refusal or intervening processing. Neither is modeled: arrivals outside `run` silently disappear ([AriadneStep.lean:95](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:95)). Define admission, refusal, and commitment before claiming stronger semantics.

4. **The ghost stamp is legitimate; durability is abstracted.** `fwd` records actual outputs and the actual pre-step counter, rather than choosing a helpful existential stamp ([AriadneStep.lean:143](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:143)). But `made` records emitted writes immediately; there is no pending-write/completion interface. `arrive; bump; tick; forward` can run at counter `2` with only the new package at counter `1`, so successful forwarding does not imply a recoverable current package under counter tampering. Restricting authenticated restores to `made` is a reasonable ideal-MAC abstraction, not inherently a weaker replay adversary. However, ordered atomic write completion hides implementation obligations. Treating torn writes as `restore none` supports fail-stop safety, not honest crash recovery.

5. **A2 is nonvacuous but narrowly conditional.** `world0; crash` witnesses its premise. [AriadneStep.lean:533](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:533) proves one specified, uninterrupted five-event recovery sequence—not eventual scheduling or progress under further crashes. The substantive lemma is that a current package always exists. That relies on `lookup` searching the complete permanent write history (line 414). Honest storage durability, overwrite behavior, and barriers therefore remain assumptions.

6. **A3’s attacks work; its control description is wrong.** The second control only proves `≠ some true` ([AriadneStep.lean:609](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:609)). I evaluated it: it returns **`none`**, because the full protocol never generated the later supplied `(2,[eh])` package. Thus the comment claiming both control traces are admissible is false. The first control fails closed; neither establishes successful recovery under those events.

7. **Listing 2 fidelity is partial; A4 is overstated.** Store-before-increment and both recovery rounds match. Purge does not: [AriadneStep.lean:155](/Users/ember/dev/degg-research/experiments/chokepoint-step/AriadneStep.lean:155) merely initializes counter zero; [ChokepointAriadne.lean:95](/Users/ember/dev/veil-pilot/VeilPilot/ChokepointAriadne.lean:95) permits purge only at boot. Actual purge increments twice and invalidates prior packages ([paper:570](/Users/ember/paperbin/strackx2016-ariadne-state-continuity.txt:570)). Gray adjacency/injectivity ([GrayCounter.lean:61](/Users/ember/dev/degg-research/experiments/chokepoint-step/GrayCounter.lean:61)) prove arithmetic facts, not power-failure atomicity, durable completion, finite-width overflow handling, or flash programming/erase behavior. [CounterWord.lean:65](/Users/ember/dev/veil-pilot/VeilPilot/CounterWord.lean:65) already assumes atomic flips.

8. **A5 conflates successful conditional obligations with induction.** Veil’s action obligations assume the entire invariant conjunction ([Induction.lean:105](/Users/ember/src/veil/Veil/Frontend/DSL/Module/VCGen/Induction.lean:105)), including `safety` clauses ([Assemble.lean:132](/Users/ember/src/veil/Veil/Frontend/DSL/Module/Util/Assemble.lean:132)). Leaving a failing clause inside that antecedent does not prove the remaining subset inductive. Reconstruction validates implications, not their missing closure. Remove the unguarded property from the proof configuration and require all obligations to pass.

**Prove next:** ordered committed-history continuity and unique binding of IDs to entries; explicit refusal semantics; durable-write-before-forward refinement; receiver deduplication correctness; and recovery over a finite counter and crashable storage implementation.
